## 摘要
将空中机器人方法从仿真推向飞行，不应需要重建成熟的自动驾驶仪或添加伴飞计算机。Cybflight 是一款开源嵌入式 Rust 研究型自动驾驶仪，其类型化、可替换的接口连接了硬件访问、感知、状态估计、轨迹规划与控制。这一模块化开发与编译期优化工作流通过可在单个 STM32H743 上运行、无需伴飞计算机的可替换 Rust 实现得到验证，包括模型预测轮廓跟踪控制（MPCTC）和增量非线性动态逆（INDI）。使用该配置，飞行器在室内飞行中达到 12.38 m/s，而使用全球导航卫星系统（GNSS）位置更新的室外飞行则达到 31.4 m/s。这些飞行表明，完全在飞行控制器微控制器上运行要求苛刻的估计与非线性控制，并不一定以牺牲模块化自动驾驶仪结构为代价。

## Abstract
Bringing an aerial robotics method from simulation to flight should not require rebuilding a mature autopilot or adding a companion computer. Cybflight is an open-source embedded Rust research autopilot whose typed, replaceable interfaces connect hardware access, perception, state estimation, trajectory planning, and control. This modular development and compile-time optimization workflow is demonstrated with replaceable Rust implementations of model predictive contour-tracking control (MPCTC) and incremental nonlinear dynamic inversion (INDI) running on one STM32H743 without a companion computer. Using this configuration, the vehicle reaches 12.38 m/s during indoor flight, while an outdoor flight using global navigation satellite system (GNSS) position updates reaches 31.4 m/s. These flights show that running demanding estimation and nonlinear control entirely on a flight-controller microcontroller need not come at the expense of a modular autopilot structure.

## 1. 核心问题与研究动机

- **核心痛点**：将空中机器人算法从仿真迁移到真实飞行时，研究者通常面临两难选择——要么重建一套成熟自驾仪，要么额外加装 Linux 伴飞计算机。
- **现有工作流的困难**：敏捷飞行研究常以成熟飞控为起点，但一旦需要替换核心估计器或控制器，设备抽象层、配置层和耦合子系统会让"局部修改"演变为大量固件特定工作，导致适配飞控栈的成本甚至超过评估算法本身。
- **常见变通方案的代价**：把底层控制留在嵌入式飞控、把实验性自主功能放到伴飞计算机上，虽然获得了更强算力，但带来额外质量、功耗、布线、软件集成与成本负担。对小型高速飞行器而言，载荷余量稀缺，每次坠机都可能损失昂贵组件。
- **总体含义**：论文主张"更换硬件或替换估计器/控制器/学习策略，不应要求重组相邻模块"，并以此为目标构建了 Cybflight。

## 2. 方法论

### 核心思想
- 采用**类型化、可替换的接口**，将硬件访问、感知、状态估计、轨迹规划、控制与执行机构解耦。
- 模块之间**交换信息而非设备句柄**：以类型化的观测、飞行器状态、参考轨迹和执行器命令作为边界。
- 在**编译期**由飞行器描述选择具体实现，使编译器能为目标微控制器特化一个 `no_std` 程序。

### 关键技术细节
- **硬件无关的研究核心**：MoCap 与 GNSS 适配器发布相同的"飞行器里程计"类型，因此更换位置源无需改动估计与控制模块；轨迹表示与参考采样也相互分离。
- **嵌入式数值核心**：使用 `no_std` 模式下的固定尺寸 `nalgebra` 类型，显式表达向量、矩阵、旋转与单位四元数，无动态分配，编译期即可捕获维度不匹配。
- **算法实现**：将模型预测轮廓跟踪控制（MPCTC）与增量非线性动态逆（INDI）实现为可替换 Rust 模块，并与所选估计器、硬件支持一起编译进同一程序。
  - MPCTC 输出集体推力与机体角速率；
  - INDI 利用角加速度与控制效能模型跟踪这些指令，再进行旋翼命令分配。
- **公式/算法示意**：Listing 1 展示了 MPCTC 与 NMPC 共享的 Gauss–Newton 姿态 Hessian，其操作数类型直接编码矩阵维度；同一模式用于模型雅可比、代价导数与滚动时域工作空间。
- **约束处理**：编译期断言（如 `const { assert!(NX >= 7); }`）与固定容量通道/工作空间保证内存使用在飞行前已知。

## 6. 主要结论与发现

- **可行性结论**：完全在单块飞控微控制器上运行高负载状态估计与非线性控制，**不必以牺牲模块化自驾仪结构为代价**。
- **性能数据**：
  - 室内最高速度 **12.38 m/s**，RMS 跟踪误差 **0.153 m**；
  - 室内时间最优 Split-S：规划路径 73.7 m，速度 11.90 m/s，RMS 误差 0.278 m；
  - 室外 GNSS 飞行最高速度 **31.4 m/s（113.04 km/h）**，三圈覆盖 438.6 m，用时 21.49 s，空域约 32.2 × 36.7 m。
- **工程结论**：类型化接口 + 编译期特化，使更换硬件、估计器、控制器或学习策略时无需重构相邻模块；固定尺寸数值类型让模型代码保持接近数学表达且可预测。

## 7. 优点

- **模块化设计清晰**：以类型化信息（观测、状态、参考、命令）而非设备句柄作为模块边界，真正实现了"换硬件不改算法、换算法不改硬件"。
- **编译期优化与内存确定性**：`no_std` + 固定尺寸 `nalgebra` + 编译期断言，使维度错误在编译期暴露，内存占用在飞行前已知。
- **无需伴飞计算机**：在单块 STM32H743 上同时运行 ESKF、20 步非线性 MPCTC 与 INDI，显著降低质量、功耗、布线与成本，对小型高速平台尤为关键。
- **高速实飞验证**：室内 12.38 m/s、室外 31.4 m/s 的全机载飞行，比纯仿真或低速悬停更具说服力。
- **开源可复现**：代码与视频均已公开，便于社区复用与扩展。
- **前瞻性路线**：明确提出嵌入式学习控制、集群飞行、离板控制三条未来路径，且都复用同一套类型接口。

## 8. 不足与局限

- **编译期组合的刚性**：更换模块需要重新编译并刷写固件，无法在运行时动态切换算法，灵活性弱于基于发布–订阅的运行时架构（如 PX4/uORB）。
- **类型系统保护有限**：固定尺寸 `nalgebra` 只能捕获矩阵维度错误，**无法捕获物理单位或坐标系约定错误**，这些只能靠模块边界的显式约定与实机验证来保证。
- **实验覆盖不足**：仅 4 页，室内约 12 组配置、室外仅 1 次飞行，缺乏重复性、统计显著性与失败案例分析。
- **无对照基准**：未与 PX4、Betaflight 桥接方案、MPCC++ 或 TinyMPC 等进行定量比较，性能优势缺乏横向证据。
- **硬件单一**：所有验证仅在一种四旋翼平台与一种 MCU（STM32H743）上完成，未展示跨平台可移植性。
- **扩展性未验证**：集群飞行、学习策略、离板控制均仅作为未来工作提出，尚无实验支撑。
- **算力边界未量化**：未讨论该架构在更复杂算法（如长时域 NMPC、视觉感知）下的算力上限，也未给出余量分析。
